# 我们给灰带加了否决，198 个真实样本里它一次没用上

> 一个 agent 记忆库的实测记录。数据、脚本、失败的部分都在。

## 先说事故

我给自己写的 agent 配了个记忆库。某天翻库的时候发现两条记忆不见了——不是标记删除，是物理 DELETE，`DELETE FROM memories WHERE key=?`。

它们去哪了？被合并进另一条了。而合并的代码在删之前做了这么一件事：

```python
nc = nc + "\n\n[合并自: %s]\n%s" % (remove_key, remove_content[:200])
```

`[:200]`。被合并的那条记忆，只留前 200 个字。剩下的部分，随着后面那行 `DELETE` 一起没了。

这是我自己写的。跑了几个月，没人发现。因为合并这个动作在日志里看起来很正常——"dedupe merged 3 pairs"，你不去翻原始内容，永远不知道丢了什么。

## 那两条记忆为什么会被判成"同一件事"

它们内容不一样。一个是"显卡 550 块"，一个是"显卡 650 块"。

用 bge-m3（1024 维，本地 llama.cpp 部署，Q4_K_M）算余弦相似度。先看**完整句子**版本：

| 一对文本 | cos | 过 0.85 | 过 0.92 |
|---|---|---|---|
| 「我买的显卡价格是550块，在闲鱼上淘的，成色还不错」<br>「我买的显卡价格是650块，在闲鱼上淘的，成色还不错」 | **0.9842** | 过 | 过 |
| 「本地部署的显存占用是2GB」<br>「本地部署的显存占用是2048MB」 | **0.9335** | 过 | 过 |
| 「我用的是 Python 3.10 跑这个项目」<br>「我用的是 Python 3.12 跑这个项目」 | **0.9698** | 过 | 过 |

三对里没有一对是"同一件事"。第一对差 100 块，第二对差 1000 多 MB，第三对是两个版本。

然后我做了个对照——把同样的差异压成短语再测：

| 同一对，短语版 | cos |
|---|---|
| `显卡550` / `显卡650` | 0.7895 |
| `2GB` / `2048MB` | 0.6581 |
| `Python 3.10` / `3.12` | 0.8600 |

**短词全都不会过 0.85 闸门，长句全都过，还过了 0.92。**

这不是"模型偶尔失误"，这是机制的必然：句子越长，相同的上下文占比越高，那点差异被平均掉了。所以真正的危险恰恰不在"两条话很像"的时候——你觉得不像的两条话，只要结构一样、只差一个数字，它就能到 0.98。

写这段的时候我把短语版和长句版都跑了，因为第一版数据我用了短语，得出"这些差异根本不危险"的结论，差点把自己的实验判成无效。


我的记忆库当时设的合并闸门是 0.92。0.9842 稳稳超过。于是 650 那条被判定为"和 550 重复"，截断、合并、删除。

## 修了什么

三件事，按重要性排：

**1. 合并不能销毁原文。** 被合并的行改成 `status='merged'` + `merged_into=<保留行 key>`，全文保留，不删。代价是库会变大——实测在 2100 条记忆上，0.85 阈值下每 100 次合并多出约 0.7 MB。这个代价我接受，因为**误合并比重复难恢复得多**。

**2. 每次合并写审计。** 新增 `merge_events` 表，记 `keep_key`、`remove_key`、合并前后的全文、`sim`、`overlap`、决策原因。现在能回答"这条记忆是什么时候、因为什么被判重复的"。

**3. 数字、单位、否定冲突时不许合并。** 就是在向量闸门后面加一道保守否决：

- 两边都有数字，且各自都有对方没有的数字 → 不合并（550 vs 650）
- 数字相同但单位不同 → 不合并（2GB vs 2MB）
- 一边有明确否定、另一边没有 → 不合并（"不能上线" vs "可以上线"）
- 一边的数字是另一边的子集 → 允许合并（"显卡550" + "显存12G"这种正常补充）

方向是**宁可少合并**。新条目多存一份，比错合并丢掉内容好。

## 然后我们做了个功能，它没用上

修完之后我还不满意：0.92 这个阈值一刀切，0.85 到 0.92 之间是个模糊地带。理论上应该让模型来判断——"这两条是同一件事的补充（延续），还是修正了旧信息，还是根本无关"。

于是设计了一套灰带机制：只有候选落在 `[0.85, 0.92)` 才去问模型，模型判"无关"就否决这次合并，判"延续/修正"就放行。阈值以上一律以向量为准，不让模型推翻。

怕它太激进，先跑 shadow：不真的否决，只记录"如果我开了，会拦下哪几条"。

拿自己记忆库里的 2100 条真实记忆，跑出 198 个灰带候选，逐个问模型。结果是：

```
延续    153
修正     14
unknown  23
无关      8
```

8 条判"无关"，理论上都该被拦。但查下来——**这 8 条全部落在已经被数字否决拦掉的那 117 条里**。

也就是说：

> 灰带否决真正独立拦下的合并数 = **0**

59% 的灰带候选（117/198）已经在更前面那道"数字/单位/否定冲突"的检查里被判了不合并，根本轮不到模型判断。剩下 81 条里，模型给的全是"延续"或"修正"，一条"无关"都没有。

所以这个功能我不开了。代码留着，默认 `off`，因为将来换了语料、换了模型，情况可能不一样——但至少在这 198 个样本上，它没有证据支持。

## 顺便说个更扫兴的

那 198 次模型调用里，有 35 次（17.7%）没拿到能解析的 JSON，走了规则降级。同一条 prompt 重跑能成功，说明是上游的瞬时抖动。

这直接影响设计：如果"无关"这个判断来自解析失败或调用超时，而代码又把"无关"当成否决理由，那系统会在随机时刻悄悄拒绝正常合并。所以我们把关系判定改成三态——`延续 / 修正 / 无关 / unknown`，`unknown` 覆盖"没候选、调用失败、解析失败、未知标签"四种情况，**只有显式 `无关` 才够格否决**。

原来那版把四种情况都塞进"无关"一个标签里，这是 bug 的温床。

## 这个方案的问题

得说清楚，不然就是在吹：

1. **只在一个 harness 上验证过。** 这套东西长在我自己的 agent 上，换框架、换调用方式，结论不一定成立。
2. **没有和 mem0 / Zep / Letta 对跑。** 我说"它们也会误合并"是推测，不是测量。要写这句就得先做实验。
3. **198 个候选来自我一个人三个月的记忆。** 样本偏窄，中文偏多，话题集中在硬件和代码上。
4. 阈值 0.85 / 0.92 是从这批数据里定的，换语料要重定。

## 结论就一句

如果你在做 agent 记忆，先去看你的合并代码有没有 `DELETE`。有的话，跑一下：拿库里最相似的一百对记忆，人工看看有几对其实不该合并。

我赌你会找到至少几对。找到之后你会明白，问题不在"合并准不准"，在"合并之后还能不能找回来"。
