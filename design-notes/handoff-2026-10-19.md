## 1. 第二种语料（issue #6）

**为什么**：agent 侧系统提示实测 46,128 字符 ≈ 26.6K tok，其中技能索引（243 份
SKILL.md 的 name+description 全量列出）占 21,486 字符 = 46.6%；单份最大技能正文
94K 字符，载入一次 ≈ 55K tok。目标是把"全量静态索引"换成"检索召出 top-k 块"。

**关键数字**（都是实跑，不是估）：

- 243 个 SKILL.md → 3,188K 字符 → 按 `##`/`###` 切 **6,762 块**（均 483 字）
- bge-m3 Q4 @ `127.0.0.1:8082`（1024 维）→ 5.6 块/秒 → 全量建库约 **20 分钟**，增量秒级
- 预实验（243 技能 / 8 个真实 query）：整句 embedding top5 命中 **6/14**，
  多实体拆开各自 top3 并集重排 **9/14（+50%）**

**方案要点**：新增两张平行表 `corpus_chunks` / `corpus_entity_links`，
**不动 `memories` 和 `entity_links`**（回滚即删表）；实体抽取复用 `_extract_entities`，
但生产前必须做三步清洗（lower 归一化 / 黑名单 / 只留出现≥2 次的实体）。

**两个必须先解决的坑**：

1. 索引必须 **chunk 级**，只索引 description 会漏——失败例「无穷小的阶 泰勒」
   两路全错，因为 `teaching-concepts-quiz` 的描述里没有主题词。
2. 实体不能靠规则词表抽，会抽出 `gen`/`web`/`agent`/`socket` 这类垃圾；
   生产走一次 LLM 调用出 JSON（flash 档够），或复用 memory.db 的 entities 表。

**验收线**：top-3 命中率 ≥ 90% 才允许替换静态索引，否则只做补充。

## 2. 合并闸门（issue #7）

**问题**：`learn()` 里锚定先跑（`lifecycle.py:1598` 得到 `relation = 延续/修正/无关`），
但合并闸门（`lifecycle.py:1665` `if fusion >= 0.85`）**不读它**。模型判"无关"照样合并，
然后把 `relation: 无关` 写到合并后的行上。

**实测数字**（本机，2026-10-19）：

```
真实 bge-m3，生产 memory.db 300 条，随机 100 对
  sim 中位 0.487  p90 0.557  p99 0.645  max 0.662   → fusion>=0.85 : 0/100
LocalHashEmbedder 兜底（嵌入服务挂掉时），同 100 对
  sim max 0.271                                     → fusion>=0.85 : 0/100
```

**所以别再重复我的错**：一开始我猜"嵌入降级 → cos 虚高 → 误合并"，数据否掉了。
hash 兜底对不同文本近乎正交（max 0.271），比真模型还干净。降级路径是安全的。
真风险只存在于**相邻但事实不同**的对（"显卡 550" vs "显卡 650"），不是随机对。

**待实施（方案已被外审推翻，别照旧方案做）**：

> ⚠️ 2026-10-19 外审（dsh headless）+ 逐条回源码复核后，原「灰带加一个 if」的方案**不成立**，
> 详见 issue #7 的评论。三条硬伤：
>
> 1. `anchoring.py` 的 `无关` 是四合一标签（真无关/无候选/LLM 失败/解析失败，138–151/206/236），
>    拿它否决合并会在 LLM 不可用时误杀合法合并 → **先三态化（加 `unknown`）**。
> 2. 合并路径不止 `1665`，还有 `1677`（慢路径）、`1787+`（实体兜底）、`deduplicate:229`、
>    `db.set()` upsert。必须抽 `_merge_decision()` 单点。
> 3. **`deduplicate()` 会物理删数据**：`344-346` 把被合并方内容截断到 200 字拼进保留行后
>    `DELETE` 整行 → 超出部分永久丢失。这是本仓库最危险的一条，优先级高于闸门。

顺带要修的合并写回 bug（都在 UPDATE 语句里）：`vector` 不刷新（旧向量继续参与匹配）、
`derived_from` 自指（绑定 `best["key"]`）、`prev_v` 记成 `pending`、`decay_profile` 被清 `None`。

**顺带**：`_fusion_score` 是乘性 boost（实体重叠≥2 → `sim × (1+0.05×min(overlap,5))`，
最多 ×1.25），`sim 0.68 + 5 个共同实体` 就够 0.85。这个 boost 目前不打日志，
线上排查"这两条为什么被合并"只能猜——建议 merge 日志补 `sim/overlap/boost`。

## 3. 实体主表（还没开 issue）

**为什么**：现在实体只是一列 TEXT + 一张关系表，**实体没有身份**。
后果可量化：`entity_links` 9,648 条 / 5,280 个实体 / 2,086 条记忆
→ 均 1.8 条/实体；`Hermes` 和 `hermes` 是两个；`assistant`/`home`/`user` 清不掉。
更关键：README roadmap 里"实体=节点，属性=带时间戳状态"这条，**没有主表就没有地方挂时间属性**。

**最小设计**：

```sql
CREATE TABLE entities (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    name          TEXT NOT NULL,              -- 显示名（保留原大小写）
    norm          TEXT NOT NULL UNIQUE,       -- 归一化键：lower + 去符号
    kind          TEXT DEFAULT NULL,          -- person/device/project/concept/tool
    aliases       TEXT DEFAULT '[]',          -- JSON 别名
    mention_count INTEGER DEFAULT 0,
    created_at    TEXT DEFAULT (datetime('now')),
    updated_at    TEXT DEFAULT (datetime('now'))
);
```

**迁移三步**（不破坏现有链路）：

1. 5,280 个现有实体归一化合并（预计降到 2,000 左右）灌进 `entities`
2. 两张 link 表各加 `entity_id INTEGER NULL`，回填
3. 检索路径先用 `entity` 字符串（不动），新写路径走 `entity_id`，验证后再切

**第 1 步的唯一风险是误合并**（`hermes` vs `Hermes Agent`、`V100` vs `V100×2`）。
5,280 里前 100 个覆盖大部分流量，人工过一遍就够，不必全审。
